# 城市政策库 · 统一数据契约 v1

> 目标：就业创业、落户、留学生四库**物理分开、契约统一**，一套引擎、一个聚合层。
> 本文件是"以后扩城/扩域/扩区都不能违反"的约定。机器可读版见 `schema.json`。

## 1. 分域与定位
| 域 domain | result_type | 现状 | 说明 |
|---|---|---|---|
| employment_startup | money（算钱） | **active**：演示域，结构到 L4 | 就业+创业+用工补贴，条件匹配+金额测算 |
| hukou | channel（选通道） | **framework**：通道清单已立、条件待采 | 一次画像可命中多条通道，输出最优路径；积分入户为排序竞争，不承诺结果 |
| overseas | review（叠加评审） | **deferred 暂缓**：仅占位 | 有客户需求再采；市级层+区级轻卡片 |

## 2. ID 编码规则（全局唯一）
- 统一：`{城市码}-{域码}-{三位序号}`，如 `XX-HK-001`（落户）、`XX-OS-001`（留学生），`XX` 为该城市的注册城市码。
- 域码：就业创业 `EMP`、落户 `HK`、留学生 `OS`。
- **历史兼容**：早期按 `POL-<城市码>-<5 位序号>` 编码的记录**保留原 ID 不重排**（避免改坏已交付数据与回归），domain 以目录为准。
- 区级追加项：在事项 ID 后加区码，如 `XX-OS-003@01`（区级叠加项）。

## 3. 统一画像（一次输入、四库共用）
- 公共字段：`kind / identities / ent_types / contract_years`；
- 各域扩展字段见 `schema.json -> unified_profile`，**跨域同义字段只能定义一次**（如社保月数、学历、年龄），各域不得另起名字；
- 引擎对画像缺失字段按类型给默认值（布尔 False、列表 []、数值 0），保证空输入不报错。

## 4. 事项统一字段与三个关键标记
- 通用字段见 `schema.json -> program_common_fields`；域内特殊字段放 `extension`，不改公共结构。
- **result_type**：money 算钱 / channel 选通道 / review 评审；
- **approval_type**：approval 核准（符合即享，可给确定结论）、planned 统筹名额、competition 排序竞争（如积分入户，只预估不承诺）、review 专家评审（只做资格预判+指引）、**auto 免申即享（由经办机构主动比对拨付，无需主动申报）**；
- **channel**：online 线上 / window 窗口 / mixed 线上线下；
- **depth（L0–L4）**：标明每条做到的细度，全市覆盖用"覆盖率×深度"衡量，不允许 L0 冒充 L4。
- 每条必须有 `version / updated_at / source_doc`，否则不算可交付数据。

### 4.1 机器字段与人读字段分离（避免一个字段塞两件事）

枚举字段供机器筛选，说明性长句另立字段。**不要把长句写回枚举字段**，否则契约门无法校验。

| 机器字段（枚举，受 gate_validate 校验） | 人读字段（自由文本） | 分工 |
|---|---|---|
| `approval_type` | `approval_detail` | 前者管「能不能给确定结论」，后者管「怎么拿到钱」 |
| `channel` | `channel_detail` | 前者管筛选与跨城统计，后者管「去哪办」 |

**`auto` 的判定边界**（易错，重点记）：
`auto` 只用于**经办机构主动发起、企业或个人无需提交申请**的场景，典型如失业保险稳岗返还「免申即享」。
只要需要**主动申报、提交材料或按季度/年度申请**，无论是否「先缴后补」，一律归 `approval`。
—— 已发现疑似误标（如某类吸纳就业社保补贴需按季度申报却标 auto），复核办法见 `待人工复核清单`。

### 4.2 申报主体的并集语义（`cond.applicant_kinds`）

**`applicant_kinds` = 受益主体 ∪ 申报主体，是并集，不是"二选一"。**

| 情形 | 写法 |
|---|---|
| 受益人和申报人都是个人 | `["person"]` |
| 受益人是个人、申报主体也可以是公司 | `["person","unit"]` |
| 创业主体（个体户/小微创办人）自己申报 | `["entrepreneur"]`；公司也能报则再加 `unit` |
| 单位自己申报自己享受 | `["unit"]` |
| 海外/留学人才 | `["overseas"]` |

四条规则：

1. **多主体 = 多条独立评估路径。** 引擎按 `profile.kind ∈ applicant_kinds` 过滤，不在其中的直接 `skip`；
   前端按主体分组提交画像（个人 / 单位 / 创业者各一套），同一条政策可能被多套画像各判一次。
2. **`cond` 引用的字段，至少要能被其中一个主体采集到**，否则那条主体路径恒为"差一点"——即**幽灵条件**。
   典型反例：`{"applicant_kinds":["entrepreneur","unit"],"must":[{"f":"biz_reg_months",...}]}`
   而 `unit` 侧根本没有"商事登记月数"控件。
3. **不要为了省事把主体写全**。并集写偏的代价是政策对某类申请人不出现（假阴性），比多出现（假阳性）更难被用户发现。
4. **同一概念的字段全局只有一个名字**：单位侧缴社保月数统一叫 `ent_ss_months`，不得在创业主体侧另起
   `hire_ss_months`（历史遗留别名已归并）。闸门第 11/12 项负责防止复发。

### 4.3 条件与标签的三条硬约束（闸门可校验）

| 约束 | 反例 | 后果 |
|---|---|---|
| 数值比较（`>` `>=` `<` `<=`）的 `v` 必须是**数值** | `{"op":">=","v":"6"}` | Python 引擎 `0 >= "6"` 抛 TypeError → 判假；前端 JS 强转 → 判真，**同一份数据两端结论相反** |
| `intersects` 的 `v` 必须是**数组** | `{"op":"intersects","v":"key_group"}` | Python `set("key_group")` 被拆成单字符集 → 恒判假；前端 `"key_group".includes(x)` → 却能命中 |
| `intersects` 的标签值必须是**前端提供的选项值** | `v:["high_tech"]` 而表单无此选项 | 用户永远选不出该标签 → 条件恒假（**标签级幽灵**） |

字段"可不可达"以 `common/field_contract.json` 为准（前端可采集字段快照，见 §10）。

### 4.4 `ptype` 的语义分裂与治理（legacy，待拆分）

`ptype` 是历史遗留字段，实测 **语义分裂为两簇**（存量条目中大量有值）：

| 簇 | 取值 | 判定 | 处置 |
|---|---|---|---|
| ① **政策产品类型** | 稳岗返还 / 残保金减免 / 税收减免 / 认定奖励·后补助 / 税收差额补贴 / 贷款贴息 / 评审资助 … | 合法用途 | **保留**；前端用它做页签与金额标签分支（`贷款贴息`→"贷款额度/贴息："等） |
| ② **主体类型** | `unit` / `person` / `entrepreneur` / `mixed` / `policy` / `channel` | **误填** | **清除** —— 该语义已由 `cond.applicant_kinds` 承载，重复且会污染前端徽标（现会显示"类型：unit"） |

**规模**：相当一部分条目属簇 ②，六种取值（`unit` / `person` / `entrepreneur` / `policy` / `channel` / `mixed`）均有出现。
**治理状态：✅ 2026-10-09 已执行**（详见 `31-字段统一决策表与执行报告.md` §2/§3.2）：
先确认前端无"靠 ptype 判主体"的逻辑（实测 5 处消费，**只做展示** + 金额标签分派，安全）→ 簇 ② **已全部清除**
（清除后只剩簇 ① 的取值）→ 簇 ① 取值域
**已写进 schema 枚举**，并由**闸门第 22 项白名单上锁**（新增值必须同改白名单与决策表）。
**不要**把 ptype 合并进 `result_type`（原 A5 描述）：`result_type` ∈ `{money,channel,review}` 是**引擎求解方式**，
ptype 是**业务标签**，二者维度不同，合并会破坏引擎分派。

### 4.5 三个链接字段的角色（别把原文页放错位置）

**同一政策可同时有「原文页」与「办事入口」，角色不同，不得混填。**

| 字段 | 角色 | 正例 | 反例（常见错位） |
|---|---|---|---|
| `guide_url` | **政策原文页（发文页）**：载有文号的官方文件页 | `fgk.chinatax.gov.cn/...`（税法法规库）、`hrss.gd.gov.cn/zcfg/...` | 栏目/清单页（点进去看不到文号）；办事指南页 |
| `apply_url` | **办事入口**：在线申报页 / 办事指南页（政务服务平台） | `gdzwfw.gov.cn/portal/v2/guide/...` | 政策原文页 |
| `source_doc` | **文号 + 出处**（**纯人读，不得内嵌 URL**；链接归 `guide_url`/`sources`）；成品「政策依据」列的唯一来源 | `演示规〔2026〕20号《…》` | 填成"另一条政策的办事指南"；写成一条裸 URL |
| `sources[]` | 官方源 URL 数组（`collector/build_sources.py` 巡检白名单输入） | — | 塞入第三方站点 |

**同页兜底**：原文页与办事入口是同一页时，只填 `guide_url`，`apply_url` 留空（见 04 §2.1 C 级）。
**机器可读版**：`schema.json -> link_field_roles`。
**核验**：L3 页面归类（原文页/指南页/入口页/登录墙/404）+ L4 角色一致 → 见 `policy_hub/链接核验运维手册.md`。

## 5. 区级政策：轻卡片挂载
- 市级层做全、做深；区级层不写复杂规则，只用 6 字段轻卡片：
  适用对象 / 补多少（档位）/ 什么时间开窗 / 申报入口 / 能否与市级叠加 / 来源文号。
- 按目标客户所在区点状扩展，未做的区标"待补"，不假装覆盖。

### 5.1 `district_awards`：市级记录内的「区县/镇街配套对照」（2026-10-10 转正）

**它解决什么**：同一事项在 A 区补 20 万、B 区补 10 万、C 区已取消 —— 这种**市级统一标准之下
的区县差异**，若强行拆成 N 条独立记录，会把一条政策撑成 N 条（客户看到的清单虚胖、去重困难）；
若丢掉不写，客户就只知道市级标准、办到区里才发现口径不同。

**与 §5「区级政策轻卡片」的分工（两者不是一回事，别混用）**

| | 形态 | 何时用 |
|---|---|---|
| §5 区级轻卡片 | **独立记录**（`level: district`，自带 id 与完整字段） | 该区政策**足以独立成条**（有自己的申报入口/窗口/条件） |
| §5.1 `district_awards` | 市级记录内的**挂载数组** | 只是「同一事项在各区县的**差异化配套标准**」，不构成独立事项 |

**结构与判据**（真值源 = `schema.json -> district_awards_fields`；闸门第 25 项校验）

- 必填键：`district`（区县/镇街名）、`first`（首次认定标准）、`renew`（重新认定标准）、
  `basis`（依据文件名 + 条款）——四者非空；
- `url` 键**必须存在**，值**可为空串**（依据原文确未公开时留空，同 §5h）；有值须 `http(s)://`；
- 可选键：`code`（区县码）/ `move_in`（迁入口径）/ `note`（该区特殊说明）；
- **键集合受白名单约束**（`DISTRICT_AWARD_KEYS`，与 `schema` 逐字同源，断言 `tests/test_district_awards.py` D4 对撞）；
- **可选字段**：整字段空 / 缺 / `null` / 空数组一律放行 —— 没有该字段的存量记录不受影响。

**渲染出口（三端分工，改渲染前先读这里）**

| 出口 | 渲染 | 说明 |
|---|---|---|
| B 端 Excel | ✅「区县配套对照」列（`mappers.district_awards_text()`） | 每区一行；`url` **不进文本**（一格只能挂一个超链接，塞多链自相矛盾） |
| 前端 `client.html` / `demo_api.html` / `_inline.js` | ✅ 卡片「区县配套对照」区块 + 清单文本行 | 有 `url` 的子项渲染「依据原文」可点链接；三处副本必须同源 |
| C 端（区县配套对照区块） | ❌ 不渲染 | C 端只收个人/创业者可申报，企业专项本就进不了 C 端成品 |

**与 `amount` 的划界**：`amount` = 市级/本级**统一**标准；`district_awards` = 下辖各区县的
**差异**部分。二者不得互相顶替，也不得在 `amount.text` 里写 `district_awards` 这类内部字段名
（该字段曾因此制造**悬空指引**：客户照文本去成品里找「逐区依据」，而当时它根本不渲染 ——
已由 `verify_output.py` **V8「内部字段名泄漏」**焊死）。

**数据形态提醒**：存量条目的 `first` / `renew` 值形态**不统一**（一部分是纯标准
「一次性 20 万元」，另一部分已自带标签「重新认定 2 万元」）→ 渲染层按
`mappers._LABEL_SYN` 的明确规则去重，**不改数据**（改值属事实层）。

## 6. 引擎与聚合层分工
- 引擎只有一套：`engine/matcher.py`（条件判定 + 金额测算），各域只提供数据/规则；
- 跨域的**去重、叠加/互斥**（同一笔不重复算、市补区补能否同享）**只在 `aggregator/aggregate.py` 处理**，不写进单域内部；
- 聚合输出统一结构见 `schema.json -> unified_output`，前端/API 只认这一种结构。

## 7. 演进路线（不要过早微服务）
1. 现在：一个仓库分目录的模块化单体（当前）；
2. 中期：聚合层外包一层只读 API（如 /match）；
3. 后期：留学生库需单独售卖/独立部署时才拆独立服务。

## 8. 合规口径（全库统一）
- 金额/积分均为规则估算，以官方最新文件与窗口审核为准；
- competition/review 类一律不承诺结果，不写"包过/保证下款"；
- 所有数值必须有 source_doc，采不到就留 null + to_collect，禁止用第三方或印象数据填充。

## 9. 数据布局约定（采集前置规则）

**本仓不附带政策数据，`domains/cities/` 初始为空。** 条目由使用者采集后填入：

| 位置 | 内容 |
|---|---|
| `domains/cities/<城市码小写>/<域>/programs.json` | 该域的政策条目 |
| `domains/cities/<城市码小写>/<域>/channels.json` | 该域的申报通道（主要用 `hukou`） |

`schema.city_code` 已登记 51 个常见城市码；要新增城市跑 `pipeline/register_city_codes.py`，
不要手改 —— 城市码有 5 个注册点，漏一个界面里就会静默消失。

**三条硬规则：**

1. **`domain` 一律以目录为准，`city` 一律以记录字段为准。**
   （历史上出现过把 `domain` 写成城市码的情况，按记录字段读会掉数据。）
2. **`overseas` 域可跨城混放，也可按城独立建目录。**
   → 新城的留学人才政策建议建 `cities/<城>/overseas/`，避免文件越滚越杂。
3. **域数不对称是正常的**：并非每城每域都有数据（`gba_tax` 只对珠三角城市有意义）。
   不要用「域数 × 城数」估算总量。

**`deadline` 目前有两种写法**（dict 与纯字符串），新采数据一律用 dict 结构：
`{mode, trigger, within_months, cycle, expire, text}`，`expire` 填日期或 `to_collect`。

## 10. 入库校验门与字段契约

`collector/gate_validate.py` 是入库前唯一的机器闸门，新采或改写的数据都要先过它。共 **25 项**：

| 项 | 内容 |
|---|---|
| 1–4 | 溯源文号/官方 URL、`result_type`+`amount`、`depth` 不虚标、区级 `district` / review 说明 |
| 5–9 | `approval_type`、`channel`、`domain` 与目录一致、`city` 与目录一致、`applicant_kinds` 枚举 |
| **10** | **同源文件同名重复**（判重三层闸门的第 3 层：同城 + 同源文件 + 同名 = 真重复） |
| **11** | **`cond` 引用字段必须在该城该身份的"控件池 ∩ 白名单"内**（防幽灵条件） |
| **12** | **条件类型规范**：数值 `v` 必须数值、`intersects` 的 `v` 必须是字符串数组 |
| **13** | **`valid` 必填且合法**（`active` / `exited` / `renamed` / `merged` / `superseded`），**必须覆盖 `channels` 型**。`merged` = 同一政策重复录入的冗余条；`superseded` = 同一事项的旧版文件（详见 §11.2） |
| **14** | **`deadline.expire` 严格 `YYYY-MM-DD` 或 `null`**：人读说明一律放 `expire_text`，不得混进 `expire` |
| **15** | **记录内禁止 `_` 前缀字段**（**递归**扫 `cond` 直属 / `cond.must[]` / `cond.any_must.conds[]`）——补丁留痕会随 payload 进 DB，破坏确权可验证性 |
| **16** | **链接基线比对**（离线读 `link_audit.json`）：只拦**新出现**的死链/已失效，存量记账不重复报 |
| **17** | **host-city 错挂**：`guide_url`/`apply_url` 的域名属地必须与 `city` 一致（客户可见字段**硬拦**，`sources` 同判据只进台账） |
| **18** | **overseas 豁免收窄**：由"整域豁免"改为**逐条**（`CITY_EXEMPT_IDS`，当前为空） |
| **19** | **必填字段非空**：`id/name/valid/result_type/approval_type/channel/source_doc`；城市目录下另要求 `city`/`domain` |
| **20** | **内容一致性回放**（离线读 `link_match.json`）：页面标题/文号 vs `source_doc`，只报 MISMATCH / DEAD |
| **21** | **`source_doc` 不得内嵌 URL**（2026-10-10 判据升级：该字段是**人读**依据，只装文号+出处）。改前只拦"孤儿"（内嵌 URL 未收录），**2026-10-10 全库 276 条已清零 → 升级为禁止**，`known_issues["orphan_doc_url"]` 已清空 |
| **22** | **字段值域白名单 + 退役字段禁回归**（字段统一「统一完成即上锁」）：`ptype`/`channel_type`/`window_type` 白名单、`sub_domain` 禁英文 slug、`obj`/`status`/`no`/`applicant` 禁回归 |

### 10.1 溯源元数据（F6 · 2026-10-09 新增三键）

把"发布主体 / 抓取日期 / 规范化文号"从 `source_doc`（人读整串、含出处）里拆成**机器可判的独立字段**：

| 字段 | 含义 | 与既有字段的边界 |
|---|---|---|
| `issuer` | 发布主体（如「广东省人力资源和社会保障厅」） | `source_doc` 是"文号 + 出处"整串人读；`issuer` 只装机关名 |
| `fetched_at` | 抓取/核验日期 `YYYY-MM-DD` | 不是政策 `date`（发布日期），是**我们核验这条的日期** |
| `doc_no` | 规范化文号（多个以「；」分隔） | `source_doc` 里文号混在长句里；`doc_no` 是纯文号 |

**为什么是"可选、空值放行"**：存量记录这三个键**全为空**，按「禁止编数据」不硬补 —— 编出来的日期/文号
比留空更危险。因此本项设计为**接入即绿**：不填不拦、填了就必须对，从而**永久防止**后续填入脏值。

第 10–12 项是 2026-10-07 补的；**第 13–15 项是 2026-10-08 补的**（对应 A8/A10 两轮：内部字段清零 + 闸门堵复发口）。起因是一次幽灵条件治理：全库一批政策引用了前端采集不到的字段，
其中一部分完全不可用，而闸门此前一项都拦不住。
**第 16–19 项是 2026-10-09 补的**（任务 #61「闸门本体补齐」）：healthcheck 早已覆盖这些检测，
闸门却只跑了 `check_one` —— 症结是**"体检绿"与"闸门绿"不是一回事**，于是一批 cross-city 记录一路溜进库。
**第 20–22 项同日补**（链接与字段影响面统一治理）：第 21 项把手工发现的"字段间不一致"脚本化，第 22 项把字段统一结果**上锁**。
**第 23 项同日补**（F6 溯源元数据）。

**`common/field_contract.json`** 是第 11 项的依据，回答"某城某身份用户到底能填哪些字段"：

```
city_kind[CITY][kind]   = 控件池(kind) ∩ CITY_FIELDS[CITY].fields[kind]
city_kind[CITY]["hukou"] = 通用落户字段 ∪ HK_EXTRA[CITY] 附加字段
kind_global["overseas"]  = collectOs() 的固定字段集
```

前端改了字段/控件后**必须重新生成**，否则第 11 项会拿旧快照判新数据：

```bash
node pipeline/extract_frontend.js && python pipeline/export_field_contract.py
```

文件缺失时第 11 项自动跳过（stdout 提示一次），不阻塞其余校验。

### 10.2 下线机制：`valid` 五值语义与三层落地（2026-10-10）

**「下线」在本项目的确切语义 = 打状态标记，不是删记录**（`promote.py` 故意不开放删除）。
五值分别对应五种**互不相同**的业务事实，机器必须能判、前端必须给出正确的客户动作：

| 取值 | 中文 | 业务事实 | 客户动作 |
|---|---|---|---|
| `active` | 现行有效 | 正常在库 | 正常申报 |
| `exited` | 已废止 | **政策本身没了**（退出实施 / 废止 / 被整合） | 不再新申报 |
| `renamed` | 已更名 | **政策还在、事项改名** | 按新事项申报 |
| `merged` | 重复录入·已合并 | **同一政策被录入两条**（同 URL / 同文号同标题） | 按保留条申报 |
| `superseded` | 已被新版替代 | **同一事项出了新版文件**（文号不同、新版声明旧版失效） | 按新版申报 |

配套字段 `exit_note` 写「依据 + 时点 / 指向」，由闸门第 24 项校验（存量走台账、只拦新增）。

**三层落地**（改动 `valid` 时三层都要看，缺一层就是"客户可见缺陷"）：

| 层 | 位置 | 现状 |
|---|---|---|
| L1 数据层 | `domains/**/*.json` 的 `valid` / `exit_note` | ✅ |
| L2 前端层 | `server/static/client.html` + `demo_api.html`（各 7 处：徽标 / 剔除推荐 / 备查分组 / 复制文案） | ✅ |
| L3 成品层 | `pipeline/export_excel.py` | ✅ **只接入 `active`**，非现役在收录阶段过滤 |

**为什么成品层要过滤而不是加状态列**：成品是**售卖的"你能申报的政策"清单**，
非现役政策放进去只会制造无效申报（客户白跑一趟）——这与前端「备查区块」的定位不同，
前端是查得到的知识库、成品是可用清单。
